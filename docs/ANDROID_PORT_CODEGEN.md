# Generated Game Code: Inputs, Pipeline, and Legal Requirements

This document traces **exactly** how the recompiled game code is produced,
what it needs, and what is automated. Everything here was verified against the
pinned submodules (`upstream` = `goliathret/EdgeOfTimeRecomp`,
`thirdparty/rexglue-sdk` = `rexglue/rexglue-sdk`).

**Bottom line: no game code exists in any public repository, and none can be
legally committed here.** The code is generated from the user's own copy of
the game. The generation pipeline is fully automated once the user supplies
two files (plus a shader-container folder for graphics); CI can run the whole
thing end-to-end without the files ever touching git.

---

## 1. The two recompiled modules

`upstream/reeot_manifest.toml` (generated by ReXGlue, committed upstream)
declares the whole codegen input set:

| Module | Input file | Output | Config files |
| --- | --- | --- | --- |
| Executable | `assets/Default.xex` | `generated/default/` | `config/reeot_default_xex*.toml`, `config/hooks/default_xex_crt.toml` |
| Game logic | `assets/Data/GameLogic.dll` | `generated/gamelogic/` | `config/reeot_gamelogic*.toml`, `config/hooks/gamelogic_crt.toml` |

`game_root = "assets"` — `assets/` is gitignored upstream ("these files can
never be committed by accident").

For each module, `rexglue codegen`:
1. Reads the PowerPC machine code from the input.
2. Splits it into functions using the boundaries in the config files.
3. Writes one C++ function per guest function into the output folder.

The generated code is compiled like any other source. `GameLogic.dll` becomes
its own shared library, `reeot_GameLogic` (via the codegen-emitted
`generated/default/dll_targets.cmake`), which the game loads the way the Xbox
360 loaded the DLL.

### The exact invocation

From `upstream/generated/rexglue.cmake` (the SDK's own build wiring):

```cmake
add_custom_command(
    OUTPUT "${CMAKE_CURRENT_SOURCE_DIR}/generated/default/codegen.build.stamp"
           ${REXGLUE_ENTRYPOINT_GENERATED_SOURCES}
    COMMAND $<TARGET_FILE:rex::rexglue> codegen ${CMAKE_CURRENT_SOURCE_DIR}/reeot_manifest.toml
    DEPFILE "${CMAKE_CURRENT_SOURCE_DIR}/generated/default/codegen.d"
    WORKING_DIRECTORY ${CMAKE_CURRENT_SOURCE_DIR}
)
add_custom_target(reeot_codegen ...)
```

i.e. **`rexglue codegen <repo-root>/reeot_manifest.toml`**, run with the
upstream repo root as the working directory. Equivalently, from the repo root:

```bash
rexglue codegen reeot_manifest.toml
```

**Codegen runs automatically as part of the CMake build.** The `reeot` target
depends on `reeot_codegen`; the stamp file + depfile make it incremental
(re-runs only when an input in `codegen.d` changes). Upstream's
`scripts/build.sh` is just `cmake --preset <p>` + `cmake --build --preset <p>` —
no separate codegen step is needed when the game files are present.

Outputs:
- `generated/default/sources.cmake` — the generated source list (included by
  `rexglue.cmake` when present, which also sets
  `REXGLUE_ENTRYPOINT_INCLUDE_DIR`).
- `generated/default/reeot_init.h` — included by `upstream/src/main.cpp:9`.
- `generated/default/reeot_pch.h` — included by `upstream/src/reeot_app.cpp:45`.
- `generated/default/dll_targets.cmake` — defines the `reeot_GameLogic` shared
  library target.
- `generated/default/codegen.build.stamp`, `codegen.d` — incrementality.

### The title update is mandatory

The port is generated from the **patched** executable: the function addresses
in `config/*.toml` match the title-updated `Default.xex`/`GameLogic.dll` only.
A clean disc copy won't match. Both files need the title update applied.

## 2. What exactly prevents gameplay (the renderer init path)

Traced through `upstream/src/reeot_app.cpp` (a `rex::ReXApp` subclass) and the
SDK's `rex_app.h`:

`ReXApp::OnInitialize` runs four phases in order:
1. **SetupEnvironment** — paths, config, logging.
2. **SetupPresentation** — `rex::ui::Window::Create(...)` (line 337:
   `window_ = rex::ui::Window::Create(app_context(), GetName(), 1280, 720)`),
   graphics provider, `VulkanPresenter`, ImGui drawer. **This is the exact
   path the Android launcher (`libedgeoftime.so`) already exercises.**
3. **OnFinalizePaths** — path resolution.
4. **ConstructRuntime** — `rex::Runtime` construction, guest GPU init,
   **XEX load**, rexcrt heap.
5. **LaunchModule** — shader cache, `PrepareModuleLaunch`, background wait.

The blockers, in the order a build hits them:

| # | Missing artifact | Effect | Where |
| - | --- | --- | --- |
| 1 | `generated/default/reeot_init.h` | **Compile error** — `src/main.cpp:9` includes it | `upstream/src/main.cpp` |
| 2 | `generated/default/reeot_pch.h` | **Compile error** | `upstream/src/reeot_app.cpp:45` |
| 3 | `generated/default/sources.cmake` | Game code not compiled into the target | `generated/rexglue.cmake:57` |
| 4 | `generated/gamelogic/` → `reeot_GameLogic` | Runtime failure when the game loads its logic DLL | codegen + `dll_targets.cmake` |
| 5 | `generated/shader_cache.cpp` | Compiles with the **empty stub** (`src/gpu/shaders/shader_cache_empty.cpp`: `g_shaderCacheEntryCount = 0`) → **the game runs but cannot draw** (upstream prints a configure-time warning: "the game will draw nothing") | `upstream/CMakeLists.txt` ~line 206-231 |

Blocker 5 deserves precision. The renderer's shader path is
`src/gpu/shaders/shader_cache.h` + `guest_shaders.cpp`: the guest (Xbox 360)
Xenos shaders are translated **ahead of time** into a cache of DXIL and
SPIR-V blobs (`g_compressedDxilCache` / `g_compressedSpirvCache` +
`g_shaderCacheEntries` indexed by shader hash). With the empty stub there are
zero entries, so no guest shader can be translated → no pipelines → no
picture. The game logic itself would still run.

There is **no runtime shader-dump fallback**: the cache is the only source of
translated shaders (`pipeline_cache.cpp` / `pso_predictor.cpp` consume
`shader_cache.h` entries; nothing regenerates them at runtime).

## 3. The shader cache: can it be generated from the user's files?

**Yes — it is generated from the user's own game files. No separate
pre-existing cache is published or required.**

Generation chain (all wired into upstream's CMake, `CMakeLists.txt` ~206-231):

```
assets/shaders/  (shader containers, one per file — extracted from the user's game data)
        │  XenosRecomp host tool (vendored: upstream/thirdparty/XenosRecomp,
        │  with vendored DXC: thirdparty/dxc-bin/lib/x64/libdxcompiler.so + bin/x64/dxc-linux)
        ▼
generated/shader_cache.cpp   (~10 minutes; upstream notes the input scan
                              touches "upwards of 7 GB of data")
```

- The build rule: if `generated/shader_cache.cpp` exists it is compiled
  directly; **else if** `assets/shaders/` (the `REEOT_SHADER_INPUT_DIR`,
  overridable) is a directory, the build generates it via
  `$<TARGET_FILE:XenosRecomp> "${REEOT_SHADER_INPUT_DIR}" "${REEOT_SHADER_CACHE_CPP}" "${REEOT_SHADER_COMMON_H}"`;
  **else** it falls back to `shader_cache_empty.cpp` with a warning.
- Manual regeneration target: `cmake --build --preset <p> --target reeot_shader_cache`
  (alias `reeot_shader_cache_regen`).
- `XenosRecomp` CLI: `XenosRecomp [input path] [output path] [shader common header]`;
  the input may be a directory (scanned, hashed, each container recompiled) —
  that is the mode the build uses.

### Where the shader containers come from (the one manual step)

Per `upstream/docs/BUILDING.md`:

> Beenox placed all the separate Shader Containers into each `.pkz` file,
> meaning you will also have to decompress via the bms script, and then run
> the shader recompiler on the entire folder.

So the containers live inside the game's `.pkz` data packages. The extraction
is: `.pkz` → unpack → shader container files → `assets/shaders/`.

In-repo tooling covers part of this: `pkztool` (built from
`thirdparty/PKZLib/tools/pkztool.cpp`) has an `unpack <in.pkz> <out.pak>`
command (`.pkz` → classic `.pak`), plus `tree`/`info`/`texture`/`strings`
inspection. The remaining `.pak` → individual shader-container files step is
the community "bms script" the BUILDING.md refers to (not vendored in this
repo); it is a user-side step performed on the user's own dump.

**Not an option:** upstream's `v1.0.0` GitHub release ships desktop binaries
(win/mac/linux) with the shader cache compiled in. Extracting or redistributing
that cache would be redistribution of content derived from the proprietary
game — not done, and not needed, since the cache regenerates from the user's
own files.

## 4. The host tools, and the cross-compiling catch

Both codegen tools are **host** tools (they run on the build machine):

| Tool | Built from | Purpose |
| --- | --- | --- |
| `rexglue` | `thirdparty/rexglue-sdk/src/rexglue/` (target `rexglue`, alias `rex::rexglue`) | `codegen`, `init`, recompile tests |
| `XenosRecomp` | `upstream/thirdparty/XenosRecomp/` (self-contained CMake project) | shader containers → `shader_cache.cpp` |

**The catch:** neither is marked host-only. `add_executable(rexglue ...)` in
the SDK and `add_subdirectory(XenosRecomp EXCLUDE_FROM_ALL)` in upstream build
them for the *target* platform. When cross-compiling for Android from an
x86_64 runner, they come out as arm64 Android executables and **cannot run on
the runner**. (EXCLUDE_FROM_ALL only keeps XenosRecomp out of the default
`all` target; the `reeot_shader_cache` custom command still builds it for the
target when referenced.)

**Therefore the pipeline builds the host tools in separate native
configures** (this is what `tools/codegen/build_host_tools.sh` does):

```bash
# 1. rexglue — native x86_64 configure of the SDK, build only the tool.
cmake -S thirdparty/rexglue-sdk -B out/host-tools/rexglue -G Ninja \
    -DCMAKE_BUILD_TYPE=Release -DREXGLUE_BUILD_TESTS=OFF -DREXGLUE_ENABLE_TRACY=OFF
cmake --build out/host-tools/rexglue --target rexglue --parallel 2

# 2. XenosRecomp — native configure of the vendored standalone project.
cmake -S upstream/thirdparty/XenosRecomp -B out/host-tools/xenosrecomp -G Ninja \
    -DCMAKE_BUILD_TYPE=Release
cmake --build out/host-tools/xenosrecomp --parallel 2
```

Both are fully self-contained: all dependencies are vendored (fmt, CLI11,
disasm for rexglue; fmt, xxHash, zstd, smol-v and DXC — including
`libdxcompiler.so` for x64 Linux and the `dxc-linux` driver — for
XenosRecomp). No network fetches, no proprietary content. These build **now**,
in CI, without any game files — which is exactly what the `host-tools` CI job
does as a regression check on the toolchain.

## 5. Automated pipeline (game files supplied via CI secrets)

`tools/codegen/` + `.github/workflows/codegen.yml` implement the full flow.
The game files enter CI **only through repository secrets** (base64-encoded),
are written to a scratch path that is gitignored, and are deleted at the end of
the job. They are **never committed, never appear in artifacts' git history,
and never leave the runner except inside the produced APK** (which itself is
only uploaded on request).

Required secrets (set by the repo owner; see `tools/codegen/README.md`):

| Secret | Content |
| --- | --- |
| `GAME_DEFAULT_XEX_B64` | base64 of the title-updated `Default.xex` |
| `GAME_GAMELOGIC_DLL_B64` | base64 of the title-updated `Data/GameLogic.dll` |
| `GAME_SHADER_DIR_B64` (optional) | base64 tar.gz of the extracted shader containers → becomes `assets/shaders/` |

Pipeline stages (`.github/workflows/codegen.yml`):

1. **host-tools** — build `rexglue` + `XenosRecomp` natively (also runs on
   every push as a regression check; no secrets needed).
2. **codegen** (secrets present) — decode the two files into
   `upstream/assets/`, run `rexglue codegen reeot_manifest.toml`, and verify
   `generated/default/sources.cmake` + `reeot_init.h` + `generated/gamelogic`
   exist. Uploads the generated code as a workflow artifact
   (`generated-game-code`, 30-day retention) so the next stage doesn't redo it.
3. **shader-cache** (secrets present) — if `GAME_SHADER_DIR_B64` was supplied,
   unpack it to `upstream/assets/shaders/` and run XenosRecomp to produce
   `generated/shader_cache.cpp` (or let the game build do it — the CMake rule
   runs XenosRecomp automatically when `assets/shaders/` exists).
4. **game-android** (needs codegen) — configure upstream for Android arm64
   with the patched SDK (`-DREXSDK_DIR=...`), build the `reeot` game code for
   arm64-v8a, and report exactly what built. (The final packaging step —
   turning the `reeot` executable target into a loadable shared library for
   the launcher's GAME BOOTSTRAP HOOK — is the remaining integration work,
   tracked in `docs/ANDROID_PORT_PROGRESS.md` M7.)

Local equivalent (no CI): `tools/codegen/run_codegen.sh <path-to-game-files>`
runs steps 2-4 on a developer machine.

### Host tools in cross builds (patches/upstream/0005)

When upstream is configured for Android from an x86_64 runner, the tools it
runs at build time (`rexglue` for codegen + the achievements dump, `pkztool`
and `pkzprep` for the UI package, `XenosRecomp` for the shader cache) are built
for the **target** and cannot execute on the runner. Patch
`0005-cmake-host-tool-overrides-for-cross-builds.patch` adds cache variables
that point those build steps at native builds of the same tools:

```bash
cmake -S android/game -B out/android-game -G Ninja \
    -DCMAKE_TOOLCHAIN_FILE="$NDK/build/cmake/android.toolchain.cmake" \
    -DANDROID_ABI=arm64-v8a -DANDROID_PLATFORM=android-28 \
    -DREXGLUE_SDK_DIR="$PWD/thirdparty/rexglue-sdk" \
    -DUPSTREAM_DIR="$PWD/upstream" \
    -DREEOT_HOST_REXGLUE="$PWD/out/host-tools/rexglue/rexglue" \
    -DREEOT_HOST_PKZTOOL="$PWD/out/host-tools/pkzlib/pkztool" \
    -DREEOT_HOST_PKZPREP="$PWD/out/host-tools/pkzprep" \
    -DREEOT_HOST_XENOSRECOMP="$PWD/out/host-tools/xenosrecomp/XenosRecomp" \
    -DREEOT_DXC="LD_LIBRARY_PATH=.../dxc-bin/lib/x64 .../dxc-bin/bin/x64/dxc-linux"
cmake --build out/android-game --parallel 2 --target reeot_game
```

The UI package authoring additionally copies fonts/textures **from the retail
`Main.pak`/`Common.pak`** (`REEOT_REFERENCE_PAKS`); supply them with the
`GAME_REFERENCE_PAKS_B64` secret (see `tools/codegen/README.md`). This is one
more user-supplied input, like the shader containers.

### Why the Android game build needs one more integration step

Upstream builds the game as an `add_executable` (`reeot`). On Android, a
native executable cannot be `dlopen`ed by the launcher; the game code must be
a **shared library** that exports `rex::ui::GetWindowedAppCreator()`
(`REX_DEFINE_APP(reeot, ReeotApp::Create)` in `src/main.cpp` defines it). The
launcher's GAME BOOTSTRAP HOOK (`android/app/src/main/cpp/edgeoftime_main.cpp`)
is where `libreeot_game.so` gets `SDL_LoadObject`ed. Concretely that means,
when the generated code exists, building on Android with the game target as a
MODULE library (or linking the recomp objects + game sources into
`libreeot_game.so` via `rexglue_setup_target`-style wiring) and adding
`reeot_GameLogic` + `libreeot_game.so` to the APK's jniLibs. This is M7 in the
progress doc.

## 6. Summary of legal input requirements

| Input | Source | Title update | Used by |
| --- | --- | --- | --- |
| `Default.xex` | user's copy of the game | **required** | `rexglue codegen` → game executable code |
| `Data/GameLogic.dll` | user's copy of the game | **required** | `rexglue codegen` → `reeot_GameLogic` |
| shader containers (`assets/shaders/`) | user's copy of the game (.pkz, via bms script) | n/a | `XenosRecomp` → `generated/shader_cache.cpp` |

Everything else — SDK, renderer, platform layer, build pipeline — is already in
this repository or built by CI.
